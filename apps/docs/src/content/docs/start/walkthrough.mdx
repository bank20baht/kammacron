Everything on this page was done for real, on 28 November 2026, with kammacron 0.0.1 from npm and
[ocr-openthai-web-demo](https://github.com/bank20baht/ocr-openthai-web-demo): an Angular app that
reads Thai documents in the browser. The cards, runs and commits in the pictures are what Claude
did then. Scroll: the window on the right follows the step you are reading.

Nothing to install first but [Bun](https://bun.sh) 1.3+, and Claude Code signed in for the agent
jobs. `bunx` fetches kammacron and starts it in the foreground; the data goes to `~/.kammacron`.

Click the `open` link: it signs this browser in, once. Later, `bunx kammacron open` does the same.
To keep it running after you close the terminal, see [install](/start/install/#keep-it-running).

<Scene title="Connect the project to the board (MCP)" bar="~/code/ocr-openthai-web-demo" alt="A terminal: kammacron token, then claude mcp add with project scope" terminal={`

    http://127.0.0.1:7420/mcp --header 'Authorization: Bearer \${KAMMACRON_TOKEN}'
Added HTTP MCP server kammacron with URL: http://127.0.0.1:7420/mcp to project config

`kammacron token` prints the `claude mcp add` line with your API token in it. For a **project**
scope server (it lives in the repository's `.mcp.json`, so anyone who opens the project gets it),
keep the token out of the file: Claude Code reads `${KAMMACRON_TOKEN}` from your environment.
Put the `export` in your shell's profile.

```json title=".mcp.json"
{
  "mcpServers": {
    "kammacron": {
      "type": "http",
      "url": "http://127.0.0.1:7420/mcp",
      "headers": { "Authorization": "Bearer ${KAMMACRON_TOKEN}" }
    }
  }
}
```

The next `claude` in the folder asks once whether to use this project's server: say yes.
`/mcp` then lists `kammacron` with its tools. kammacron's own cron jobs do not need this file:
each of their runs gets a token of its own.

</Scene>

Put a skill in the repository, `.claude/skills/add-card/SKILL.md`, so Claude asks the questions
that matter and then writes the cards with the board's MCP tools. In short, it says:

1. `list_projects`, and take the project whose directory is this repository.
2. Ask one question at a time, with the answer you would pick; read the code before asking what it
   can answer; `list_cards` first, so nothing is filed twice.
3. Propose the cards: `auto-pilot` for reversible work with a clear done condition, `human: true`
   for security, data, deploys or product decisions.
4. After the go-ahead, one `create_cards` call. Do not start the work.

In a session you just type `/add-card` and your idea, and answer its questions. For the picture we
ran it once with `claude -p` and told it to answer its own questions with the answers it would
pick: that is the Thai reply on the right, card #2 and the choices it made.

Give it a name of its own: a skill in `~/.claude/skills` with the same name wins over the
project's (ours was first called `add-task`, and a personal `add-task` took the call).

</Scene>

<Scene title="CLAUDE.md: work only from the board" bar="~/code/ocr-openthai-web-demo" alt="The repository's CLAUDE.md, saying the board is the only list of work" terminal={`
$ sed -n '6,$p' CLAUDE.md
# Work comes from the kammacron board

This repository's work lives on its kammacron board (project \`ocr-openthai-web-demo\`, MCP server
\`kammacron\`). The board is the only list of what to do.

- **Only work a card.** Before changing code, find its card (\`list_cards\`, \`get_card\`). Asked for
  something that has no card? Make one first (the \`add-card\` skill), then work it.
- **Take it, then do it.** \`move_card\` to \`doing\` when you start. Work only on what the card says;
  anything else you notice becomes a new card, not part of this change.
- **Write the result on the card.** \`add_comment\` with what changed, the files, and how you checked
  it (\`bun run test\`, \`bun run typecheck\`). Then \`move_card\` to \`done\`.
- **Stuck or unsure?** \`move_card\` to \`review\` with the reason and the question. Never guess on
  security, data, deploys or a product decision; never skip a test to pass.
- **One card, one commit**: \`fix(web): <what> (#<card>)\`, on the branch you were started on. Do not
  push, and do not create or switch branches.
- A card tagged \`human\` is a person's: do not take it.
  `}>

Claude reads `CLAUDE.md` in every session in this folder, yours and kammacron's runs alike. Say
there that the board is the one list of work, how a card is taken and finished, and what an agent
must leave to a person. kammacron's runs work the directory as it is (it does not branch, reset or
push), so say in `CLAUDE.md` how to commit, and whether to push.

</Scene>

<Scene title="Its prompt" bar="127.0.0.1:7420/cron" image={huntTask} alt="New cron job, step 2: the bug-hunting prompt, Use the Kanban board unticked, Sonnet picked">

```text
Look for real bugs in apps/web/src: wrong behaviour, an error nobody
handles, an edge case that breaks. Read the code; do not change any file.

For each bug you are sure of, file one card on the kammacron board
(create_cards, this project): the title says what goes wrong, the body has
the file and line, how to see it, and "Done when". Tag it "bug" and
"auto-pilot" when the fix is small and a test can prove it; otherwise set
human=true.

First list_cards with the tag "bug": never file one twice. At most 3 cards
a run. Nothing found? Say so and file nothing.
```

Untick **Use the Kanban board**: that hands the job cards to _take_, and this one only files them.
**More options** picks the model.

</Scene>

<Scene title="When it runs" bar="127.0.0.1:7420/cron" image={huntWhen} alt="New cron job, step 3: weekdays at 09:00">

Like an alarm clock: weekdays at 09:00 (`0 9 * * 1-5`). To see it work now, set **Cron** to
`* * * * *`, wait for the first run to start (the next whole minute, plus up to 30 seconds), then put
the time back.

</Scene>

<Scene title="It runs" bar="127.0.0.1:7420/runs/1" image={huntRun} alt="Run 1: succeeded, 1 minute 4 seconds, 26 turns, $0.50; the timeline of its tool calls">

**Runs** shows each one live: every tool call and its result. This one read the scan page and the OCR

<Scene title="Three bugs on the board" bar="127.0.0.1:7420/board/ocr-openthai-web-demo" image={boardBugs} alt="The board: four cards in To do, three of them bugs; one is tagged Human">

It filed three real bugs, each with the file and line, how to see it and when it is done:

- **#3** editing the text while digits are shown in Thai turns every digit on the page, for good:
  marked **Human**, because what it should do is a product decision;
- **#4** after the OCR worker fails to load, _retry_ hangs forever: `auto-pilot`;
- **#5** one unreadable image in a batch stops every page after it: `auto-pilot`.

</Scene>

<Scene title="Cron job 2: fix them, one card a time" bar="127.0.0.1:7420/cron" image={fixTask} alt="New cron job Fix bugs: the prompt, Use the Kanban board ticked">

```text
Take one auto-pilot card, do it, and write the result on the card.
Follow CLAUDE.md: run the tests, one commit for the card.
```

This time keep **Use the Kanban board** ticked: each run gets the open `auto-pilot` cards and how to
take one. A card tagged `human` is never handed out.

</Scene>

<Scene title="Every five minutes" bar="127.0.0.1:7420/cron" image={fixWhen} alt="New cron job, step 3: every 5 minutes">

**Every few minutes** → 5. Each run takes one card; a run that finds none ends at once. Every hour, or
every night, suits a real project better: you read the results in the morning.

</Scene>

<Scene title="Two jobs, one project" bar="127.0.0.1:7420/cron" image={cronList} alt="The project's cron jobs: Find bugs (weekdays 09:00) and Fix bugs (every 5 minutes, with the board), both on">

**Turn off** stops a job and keeps it; **Edit** changes it. The **Calendar** shows when each one runs
next.

</Scene>

<Scene title="Watch: the board and the app" bar="127.0.0.1:7420/board | localhost:4200" images={[watchBoard, watchDev]} alt="Left, the board: #5 in Doing, #4 and #2 in Done; right, the app with a picked page and the new clear-all button">

Keep the board on one side and the dev server (`bun run dev`) on the other. Each run moves its card
to **Doing**, then to **Done** with a comment, or to **Review** with a question; the dev server
reloads with the fix. Here #4 is done, #5 is being worked, and the app already has the
**ล้างทั้งหมด** (clear all) button that card #2 asked for.

</Scene>

<Scene title="What it wrote on the card" bar="127.0.0.1:7420/board/ocr-openthai-web-demo" image={cardDone} alt="Card #2 done: the agent's comment with what changed, what it decided, and the tests it ran">

Open a card for what was done. On #2 the agent wrote the commit, the files it changed, what it
decided on its own (and why), and what it ran: `bun run test` 89/89, typecheck, lint, format. A card in **Review** waits
for you in **Review**, with the reason: approve it, or send it back with a note for the next run.

</Scene>

The whole afternoon: one hunting run and three fixing runs, 15 minutes from the first hunt to the
